# LINE Messaging API × GAS 汎用開発ガイドライン＆ベストプラクティス

本ドキュメントは、LINE Bot開発（特にGoogle Apps Scriptやサーバーレス環境）におけるアーキテクチャ設計、API仕様、制約事項、アンチパターンおよびトラブルシューティングを包括的にまとめた恒久ナレッジです。

---

## 1. 通信・レスポンス設計（最重要）

### 1-1. `replyToken` の有効期限と同期処理の厳禁
- **有効期限**: ユーザーのメッセージ送信から **約1〜3秒以内**（最大でも数秒）。
- **一度きりの使い捨て**: 1つの `replyToken` に対して返信できるのは **1回のみ**（配列で最大5メッセージまで同時に送ることは可能）。2回目の呼び出しは 400 エラーになる。
- **外部API（LLM・重いスクレイピング）の同期実行はNG**:
  - LLM推論や重い処理に4秒以上かかると、replyToken が失効して **「既読スルー（無反応）」** になる。
  - **対策**:
    - 即答可能な辞書・ルールベースを優先する。
    - LLM等の外部通信はタイムアウト（1.5〜2秒未満）を設定し、間に合わない場合はフォールバックメッセージを返す。
    - または、即時 `replyToken` で「お調べしています…」と返し、完了後に `pushMessage`（※要送信枠確認）で送る設計にする。

### 1-2. LINEプラットフォームからのWebhook検証
- **空イベント対策**:
  - LINE Developersコンソールでの「Webhookの検証」ボタン押下時、`events` 配列が空（`[]`）のリクエストが飛んでくる。
  - `events[0]` を前提にコードを書くと `TypeError` で落ちて検証が失敗する。
  ```javascript
  if (!e || !e.postData) return ContentService.createTextOutput("OK");
  const json = JSON.parse(e.postData.contents);
  if (!json.events || json.events.length === 0) return ContentService.createTextOutput("OK");
  ```
- **必ず HTTP 200 を返す**:
  - Webhook受信処理（`doPost`）内で例外がスローされ 500 等を返すと、LINE側が「Webhookサーバー障害」と判断して再送または配信停止を行う場合がある。全体を `try...catch` で保護し、エラー時も 200 OK を返すこと。

## 2. コスト・メッセージ種別の使い分け

| 種別 | 送信方法 | コスト（従量課金） | 用途 |
| :--- | :--- | :--- | :--- |
| **応答メッセージ** (`replyMessage`) | `replyToken` を使用 | **完全無料**（枠消費なし） | ユーザーからの発話に対する直接の返信 |
| **プッシュメッセージ** (`pushMessage`) | `userId` を指定 | **送信枠を消費** | 定期配信、リマインダー、非同期処理の完了通知 |

- 基本はすべて `replyMessage` で設計し、コストと枠の消費をゼロに抑える。

## 3. UI/UX コンポーネントの制約とベストプラクティス

### 3-1. Flex Message（リッチなカード・カルーセル）
- **カルーセルのバブル数制限**: 1つのカルーセルに含められるバブルは **最大12個** まで（多すぎると横スクロールが煩わしくなるため、実務上は **3〜5個** が最適）。
- **画像の表示比率**: サムネイル画像は `16:9`、`1:1`、`20:13` などを明示し、`aspectMode: "cover"` を指定してアスペクト比崩れを防ぐ。
- **文字数制限**: テナント表示崩れを防ぐため、タイトルは `maxLines: 2`、`wrap: true` を指定する。

### 3-2. QuickReply（画面下部のワンタップボタン）
- **最大表示数**: **13個** まで。
- **ボタン文字数制限**: `label` は最大 **20文字** まで（超えるとエラー）。
- **用途**: 0件ヒット時の「次の検索ワード提案」、分岐選択肢、確認ダイアログの代替として最も摩擦が少ない。

### 3-3. テキストメッセージ
- **文字数制限**: 1吹き出しあたり **最大5,000文字**。
- **読みやすさ**: スマホ画面での可読性を保つため、1メッセージは3〜5行程度に抑え、要点は改行・絵文字で区切る。

## 4. 検索・入力処理の堅牢化

### 4-1. 1文字ノイズ誤爆の防止
- ひらがな・カタカナ・アルファベット1文字（「あ」「い」「a」など）は、あらゆる日本語の文章・目次に部分一致してしまい、無意味な検索結果を大量に返してしまう。
- **ルール**:
  - ひらがな・カタカナ・英数は **2文字以上** から検索実行。
  - 1文字の場合は「2文字以上の専門用語を入力してください😊」と優しいガイドメッセージを返す。
  - ただし、医学・専門用語として成立する **漢字1文字（骨、脳、胃、肺、肝、腎、熱 など）は検索を許可** する。

### 4-2. 全角・半角スペースと大文字・小文字の正規化
- ユーザーの入力は多種多様：全角スペース（`　`）、大文字英数（`ＡＢＣ`）、ひらがな/カタカナ。
- 検索処理前に `replace(/　/g, ' ').trim().toLowerCase()` などで正規化してから単語分割を行う。

## 5. セキュリティと認証情報管理

1. **シークレットのハードコード禁止**:
   - `CHANNEL_ACCESS_TOKEN` や 各種APIキーはコード内に直書きしない。
   - GASの `PropertiesService.getScriptProperties()`（スクリプトプロパティ）に逃がす。
2. **長期アクセストークンを使用する**:
   - LINE Developersのチャネル設定で発行するアクセストークンは、「短期（有効期限30日）」ではなく **「チャネルアクセストークン（長期 / v2.1）」** を使用する（期限切れによる突然の停止を防止）。
